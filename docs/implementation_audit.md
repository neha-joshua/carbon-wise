# CarbonWise implementation audit

Initial audit: 2026-10-20; evidence updates: 2026-10-24 through 2026-10-26. The uploaded ZIP was compared with the extracted project copy (excluding its local virtual environment); the extracted copy was newer and used as the source of truth. Work was done in a separate working copy, preserving the original starter CSV and uploaded archive.

## Application and data

- `dashboard/app.py` is a Streamlit local application. Its launch instructions use `streamlit run app.py` from `dashboard/`; no live GCC, sensor, or municipal API connection was found.
- `src/digital_twin.py` is a scenario state-copy and re-optimisation layer: it applies hypothetical vulnerability, population, cost, or budget changes to local tabular data. It is not a physical simulation or live connected twin.
- `data/raw/projects.csv` is generated by `data/raw/generate_projects.py`; the generator uses seeded random draws from broad benchmark ranges to create 56 candidate records. It is synthetic/benchmark-grounded, not 56 verified GCC tenders.
- `data/raw/wards.csv` has 15 records with `zone_id` values. Despite the filename, these are GCC zones, not wards. Their reported vulnerability/population provenance requires primary-source audit before calling the numerical values verified.
- Rule-based modules exist in `src/agents.py`; optional LLM explanation code exists in `src/llm/`. Neither constitutes autonomous multi-agent LLM decision-making. The optimizer itself is `pymoo` NSGA-II.
- Existing dashboard, scenarios, report, sensitivity, baseline, audit, and rationale modules are present. Their existence does not validate the numerical claims in the supplied review report.

## Important implementation risks found

- `src/preprocessing.py` median-imputes numeric nulls, which can silently turn unknown impact into a plausible numeric input.
- `src/optimizer.py` sums normalized project scores as additive portfolio objectives. The units and interpretation differ from physical tCO2e and resilience outcomes.
- `src/equity_auditor.py` audits the investment share assigned to zones over a hard-coded vulnerability threshold; it is not an independent outcome-benefit measure and uses the optimizer dataset's estimated costs.
- `src/evaluate_equity.py` adds a 50/50 weighted greedy comparator and independently calculates Gini, Theil T, and Atkinson distribution measures for modeled investment per resident. These recalculate the allocation distribution, but still use generated project costs and unvalidated zone denominators; they do not establish real-world equity impacts.
- The supplied GCC starter contains 23 rows, including 2 programme aggregates, estimates, unknown impact, and mixed scopes. None has a compatible zone identifier plus a supported resilience input and reconciled cost basis. The derived model-ready dataset is intentionally empty.
- Official TN eProcurement pages confirm tender IDs, package titles, and publication dates for three distinct work packages. ADB's primary project page lists matching contracts under Loan 4113, including award dates, contractors, original-USD contract totals, and ADB-financed components. Tender estimates show `NA` where visible; actual expenditure, completion status, and physical quantities remain unverified.

## Claims to revise in Review 2 materials

The report's claims of real ward-level project data, fully verified optimisation, 92% investment to high-vulnerability zones, and a verified 17% resilience / 9% equity improvement are not supported by the checked data/code artifacts. The included candidate projects are generated synthetic benchmark samples, and the equity constraint/audit share the same underlying investment allocation. Present previous percentages as outputs from the previous synthetic model run only if reproducible from that exact version, clearly labelled as modelled, and remove claims of independent validation. No historical allocation backtest is available in the inspected project.

## Current milestone

Added a tender dataset with primary portal notice details and ADB award details while leaving actual expenditure and physical quantities unknown. See `docs/data_provenance.md` and `docs/drainage_tender_methodology.md`.

The default experiment uses five NSGA-II seeds; the checked smoke run used seed 1, population 40, and 50 generations. Both remain generated-data experiments, not a historical backtest.

The prior optimizer remains available in a separate synthetic scenario lab.
